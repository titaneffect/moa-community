# 복구 가이드

## 1. 문서 범위

DB 덤프를 별도 테스트 계정으로 복원하는 검증은 완료했습니다.
새 서버에 앱·DB·첨부파일·HTTPS를 모두 복구하는 절차는
아직 전체 검증하지 않았습니다.

아래 내용은 복구 준비와 작업 순서를 정리한 초안입니다.

## 2. 복구에 필요한 자료

| 자료 | 확보 위치 |
|---|---|
| 애플리케이션 코드·배포 설정·스크립트 | Git 저장소 |
| 앱 Docker 이미지 | Docker Hub |
| DB 덤프 및 export 로그 | DB 백업 S3 버킷 |
| 첨부파일 | 첨부파일 백업 S3 버킷 |
| app.env, oracle.env 등 환경 설정 | 별도 보관한 설정 자료 |
| 인증서·갱신 설정 | 기존 서버에서 확보하거나 새로 발급 |

백업 버킷:

- DB: `deepstudy-db-backups-406579089357-ap-northeast-2-an`
- 첨부파일: `deepstudy-attachment-backups-406579089357-ap-northeast-2-an`

리전은 `ap-northeast-2`입니다.

EC2 내부의 백업과 Oracle 볼륨만으로는
인스턴스·디스크 손실에 대비할 수 없으므로 외부 백업을 사용합니다.

## 3. 백업 선택

### DB

정상 완료된 export 로그와 짝이 되는 `.dmp` 파일을 선택합니다.

예:

```text
scott-YYYYMMDD-HHMMSS.dmp
scott-YYYYMMDD-HHMMSS.log
```

파일명이 최신이라는 이유만으로 선택하지 않고,
export 로그의 정상 완료 기록도 확인합니다.

### 첨부파일

S3의 `attachments/` 아래에 있는 파일을 사용합니다.
하위 폴더 구조를 유지해야 DB에 기록된 경로와 연결할 수 있습니다.

DB 백업과 첨부파일 백업은 별도 시각에 실행됩니다.
동일 시점의 스냅샷이 아니므로 복구 후
DB 메타데이터와 실제 파일의 대응을 확인해야 합니다.

## 4. 새 서버 준비 순서

아래 절차는 새 서버에서 전체 검증이 필요합니다.

1. 현재 Oracle 이미지에 맞는 서버 OS·CPU 환경 준비
2. Docker와 호환되는 Docker Compose 설치
3. AWS CLI 설치 및 백업 다운로드 권한 설정
4. 코드·배포 설정·운영 스크립트 확보
5. 환경 설정 파일 복원
6. 작업 폴더와 첨부파일 폴더 생성
7. Oracle 외부 볼륨 `oracle-data` 준비
8. Oracle 기동 및 DB 접속 확인
9. DB와 첨부파일 복구
10. 앱 기동 및 기능 검증
11. DNS·HTTPS·Nginx 구성
12. 시간대·cron 설정 및 백업 검증

현재 설정은 아래 경로를 사용합니다.

- 작업 폴더: `/home/ubuntu/deepstudy-deploy`
- 첨부파일: `/home/ubuntu/deepstudy-uploads`
- Oracle 볼륨: `oracle-data`
- DB 서비스명: `FREEPDB1`
- 운영 DB 사용자: `SCOTT`

경로를 바꾸면 Compose, 스크립트, cron도 함께 수정해야 합니다.

현재 Compose의 앱 설정은 `format: raw`를 사용하므로
이를 지원하는 Compose 버전이 필요합니다.

Oracle 컨테이너와 원본 첨부파일 폴더의 접근 권한도 확인합니다.
첨부파일 권한은 실제 앱 실행 사용자에 맞춰 설정합니다.

현재 배포 워크플로에는 Nginx IP `172.19.0.2` 확인이 포함되어 있습니다.
새 서버에서는 실제 Nginx IP와 Tomcat의 신뢰 프록시 설정을
함께 확인해야 합니다.

## 5. DB 복구

Data Pump 복구의 작업 순서는 다음과 같습니다.

1. 선택한 `.dmp`와 `.log` 다운로드
2. 덤프를 Oracle 컨테이너가 읽을 수 있는 폴더에 배치
3. `FREEPDB1`에 복원 대상 계정과 필요한 권한·공간 준비
4. 덤프 폴더를 가리키는 Oracle DIRECTORY 객체 준비
5. `impdp`로 복원
6. import 로그와 복원된 객체·데이터 확인

기존 서버의 덤프 폴더는 다음과 같습니다.

```text
/opt/oracle/oradata/scott-backups
```

기존 DIRECTORY 객체 이름은 `SCOTT_BACKUP_DIR`입니다.
새 DB에서는 폴더와 DIRECTORY 객체를 다시 준비해야 합니다.

다른 계정으로 복원할 경우 `REMAP_SCHEMA`를 사용합니다.

```text
REMAP_SCHEMA=SCOTT:복원대상계정
```

실제 `impdp` 명령은 대상 계정·DIRECTORY·덤프 이름·권한을
확인한 뒤 작성합니다.

### 초기화 SQL과의 구분

`sql/create_tables.sql`과 `sql/create_sequences.sql`은
데이터 없이 새 DB 구조를 만드는 용도입니다.

스키마 구조가 포함된 Data Pump 덤프로 복구할 때는
초기화 SQL을 먼저 실행하지 않습니다.
기존 객체를 대상으로 복원하는 경우에는 별도의 import 정책이 필요합니다.

### 복원 검증

원본 또는 백업 시점의 기록과 비교합니다.

- 테이블·시퀀스·인덱스 수
- 테이블별 행 수
- INVALID 객체 유무
- 제약조건과 인덱스 상태
- 앱의 읽기·쓰기 동작

신규 데이터 등록도 확인하여
시퀀스로 생성한 ID가 기존 데이터와 충돌하지 않는지 점검합니다.

기존 테스트에서는 테이블 8개·시퀀스 6개·인덱스 11개와
테이블별 행 수 일치, INVALID 객체 없음을 확인했습니다.

## 6. 첨부파일 복구

S3의 `attachments/` 내부 파일을 다음 경로로 복구합니다.

```text
/home/ubuntu/deepstudy-uploads
```

`attachments/` 폴더 자체를 한 단계 더 만들지 않고,
그 내부의 날짜별 폴더가 업로드 폴더 아래에 오도록 합니다.

예:

```text
/home/ubuntu/deepstudy-uploads/2026/10/09/파일
```

복구 후 확인할 내용:

- 날짜별 하위 경로 유지
- 앱의 읽기·쓰기 권한
- 기존 본문 이미지 표시
- 기존 첨부파일 다운로드
- 새 파일 업로드

S3에는 서버에서 삭제된 파일이 남아 있을 수 있습니다.
복구 파일을 모두 현재 사용 중인 파일이라고 판단하지 않습니다.

DB 덤프에는 첨부파일 메타데이터만 포함되므로,
실제 파일은 별도로 복구해야 합니다.

## 7. 앱·HTTPS 복구 후 확인

- 앱의 DB URL·사용자·비밀번호
- 첨부파일 볼륨 연결
- Tomcat의 신뢰 프록시 설정
- 도메인의 새 서버 IP 반영
- 인증서 파일 또는 새 인증서 발급
- Nginx 설정 검사
- HTTPS 접속과 로그인
- 게시글 조회·등록 및 첨부파일 동작

기존 Nginx 설정은 인증서 파일이 존재해야 시작할 수 있습니다.
인증서가 없다면 발급용 HTTP 설정을 먼저 준비해야 합니다.

## 8. 예약 작업 복구

cron은 GitHub Actions가 자동 등록하지 않으므로
새 서버에서 직접 등록합니다.

- ubuntu: 인증서 확인, DB 백업
- root: 첨부파일 백업

로그 폴더를 먼저 준비하고 서버 시간대를 확인합니다.
수동 백업을 먼저 검증한 뒤 예약 시각의 실행도 확인합니다.

명령과 cron 내용은 [운영 가이드](operations.md)를 참고합니다.
